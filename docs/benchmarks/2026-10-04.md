## Como reproduzir

```text
# server (bench do sim contra o dev_server, que só existe em debug)
cargo run -p padgaming-net --example dev_server -- --mock
cargo run -p padgaming-sim -- bench --insecure-dev --clients 4 --rate 250 --duration 60s --json bench.json
node scripts/bench-gate.mjs bench.json docs/benchmarks/baseline.json

# UDP → XInput e CPU (precisam do ViGEmBus instalado)
cargo test -p padgaming-server --release --test xinput_latency -- --ignored --nocapture --test-threads=1
```

Dados brutos: [`sim-bench-2026-10-04.json`](sim-bench-2026-10-04.json), que também é a base do gate
([`baseline.json`](baseline.json)).

## Gate de regressão

O job `bench` do CI sobe o `dev_server --mock`, roda 20 s de bench e chama `scripts/bench-gate.mjs`.
Falha se o p99 do server passar de 1 ms, se crescer mais de 20% sobre a base (com piso de 100 µs na
base, porque runners compartilhados oscilam nessa escala) ou se os pings ficarem sem resposta.

## Como medir RAM e abertura

O binário precisa do frontend embutido: `pnpm --filter @padgaming/desktop build` e depois
`cargo build --release -p padgaming-desktop --features tauri/custom-protocol` (ou `tauri build`).
Um `cargo build --release` puro carrega o `devUrl` e mostra "localhost recusou a conexão".
A abertura é o tempo entre iniciar o processo e a linha `primeira tela pintada` aparecer no log
(`%LOCALAPPDATA%\PadGaming\logs`). A RAM soma `padgaming-desktop.exe` e os `msedgewebview2.exe` do
app, 10 s depois de abrir; a janela fechada na bandeja usa `--minimized`.

## Meta que falhou

RNF-03 com a janela aberta: 234 MB privados (450 MB de working set) contra 150 MB. Quase tudo é o
WebView2 (6 processos); o backend em Rust usa ~43 MB. Fica para uma task de otimização (por exemplo,
destruir a janela ao ir para a bandeja, que o app já faz, e reduzir o que a UI carrega). Na bandeja a
meta é cumprida com folga.
